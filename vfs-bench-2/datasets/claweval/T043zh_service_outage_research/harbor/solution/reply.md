# CloudPay 支付故障调研报告（2026-03-01）

本报告只做调研和分析，未执行任何实际操作：没有切换支付网关、没有发送通知、没有联系供应商。信息来源：CloudPay 官方状态页（status.cloudpay.com，事件 INC-20260301-001）、CloudPay 工程博客、CloudPay 开发者社区、AsiaPay 集成文档、PCI SSC 事件响应指南、Fintech Insights 的支付故障成本分析。

## 一、故障概要

| 项目 | 内容 |
|---|---|
| 受影响服务 | CloudPay 支付网关（我们的主支付通道） |
| 开始时间 | 2026-03-01 14:30 UTC（北京时间 22:30）监控发现错误率上升；根源部署在 14:00 UTC |
| 影响范围 | 仅亚太（Asia-Pacific）区域；美国、欧洲区域和 Dashboard 不受影响 |
| 症状 | 支付 API 约 60% 的请求返回 503；退款 API 完全不可用；Webhook 推送积压超过 45万（450,000+）条 |
| 事件状态 | Investigating（状态页 17:30 UTC 更新），回滚进行中 |

**根因**：CloudPay 在 14:00 UTC 向亚太数据库集群部署 **v3.2.1** 版本，其中包含对核心表 **`payment_transactions`**（2.3TB，约 18 亿行）的 schema 迁移（数据库迁移）：为提升查询性能添加复合索引 `idx_merchant_date`。在 PostgreSQL 上普通 `CREATE INDEX` 会持有 **SHARE 锁**，阻塞了全部 INSERT，**锁争用**进而耗尽了 500 连接的**连接池**，引发级联超时和 503。预发布环境的同名表只有 5 万行，所以测试没有暴露问题。

## 二、当前状态和预计恢复时间

- **17:00 UTC** 开始**回滚**迁移，但需要重建原索引结构，受 2.3TB 表体积拖累，慢于预期。
- **18:00 UTC** **部分恢复**：支付 API 成功率从约 40% 回升到约 **75%**（失败率约 25%）；退款 API 仍不可用；Webhook 仍在积压，恢复后会按顺序重放。
- **预计完全恢复：22:30 UTC**（北京时间 3 月 2 日 06:30），即故障开始后约 **8 小时**。下一次官方更新 19:00 UTC。
- CloudPay 承诺向受影响商户提供服务抵扣，细则 7 个工作日内公布；并给出了预防措施（强制 `CREATE INDEX CONCURRENTLY`、大表部署审批、亚太部署窗口改到 02:00-06:00 UTC、预发布环境用生产规模数据）。
- 背景：这是 CloudPay 12 个月内第二次重大故障（2025 年 9 月负载均衡器配置错误导致全球宕机 4 小时），其 2025 年可用率 99.92%，低于 99.99% 的 SLA 承诺。

## 三、对我们业务的影响评估

1. **支付转化**：从今天下午（北京时间 22:30 起）到预计恢复的次日 06:30，亚太区约 60% 的支付请求失败（18:00 UTC 后约 25%），我们的商城客户支付频繁失败与此完全吻合。
2. **退款**：退款 API 整段时间不可用，期间提交的退款会排队，恢复后才处理，客服需要对退款咨询有统一口径。
3. **订单状态同步**：Webhook 积压 45 万条以上，即使支付 API 恢复，支付成功通知也会延迟数小时；如果订单履约依赖 Webhook，会出现"已付款但订单未更新"的情况，需要改为主动轮询支付状态。
4. **财务影响**：按 Fintech Insights 2026 年的分析，中型商户（年 GMV 100 万至 5000 万美元）在支付网关宕机期间平均每小时损失 **$35,000-$50,000**（3.5 万至 5 万美元）的直接收入；按 8 小时估算，直接损失约 28 万至 40 万美元量级，需按我们实际交易量折算。间接成本通常是直接损失的 2-3 倍：支付失败的客户 15-20% 在 30 天内不会回来（客户流失），支付失败使购物车放弃率上升 40-60%，客服量激增 300-500%。
5. **合规**：见第五节，72小时内有向收单行报告的义务。

## 四、建议的应急措施

**短期（今晚）**

1. **队列加重试（Queue and Retry）**：CloudPay 返回 503 时不向客户报错，把支付意图写入本地队列（Redis 或数据库），页面显示"支付处理中"，按指数退避重试（30 秒、60 秒、120 秒、300 秒）；3 次失败后切换到备用通道，5 次失败后提示客户稍后再试。**务必使用幂等键**，防止重复扣款。社区实测可减少 70-80% 面向客户的失败。
2. **路由到美西端点**：CloudPay 的 **us-west.api.cloudpay.com** 不受影响，可把亚太交易临时改走该端点，延迟增加约 200ms；注意只对创建支付有效，退款仍走亚太基础设施。
3. **Webhook 兜底**：对支付状态改为主动轮询，不要缓存重放 Webhook 事件（可能是过期数据）；看到少量成功请求也不要当作已恢复，目前是间歇性的。
4. **客户沟通**：前台提示支付延迟，客服准备退款排队的说明。

**备选支付方案（紧急切换可行性）**

- **AsiaPay** 提供与 CloudPay **API 兼容**的"兼容模式"，官方称**紧急迁移 30 分钟**：注册账户（5 分钟）、把端点 `api.cloudpay.com` 改为 `api.asiapay.com` 并换成 AsiaPay 的 Bearer 密钥（10 分钟）、在 `sandbox.api.asiapay.com` 测试（15 分钟）。Webhook 载荷结构兼容，退款 API 即时可用，货币代码同为 ISO 4217。
- **唯一字段差异**：AsiaPay 用 `merchant_ref`，CloudPay 用 `merchant_reference`，切换前必须改掉这一处。
- 费率：标准 2.9% + $0.30，紧急迁移前 30 天 2.5% + $0.25，无开通费和月最低消费；结算 T+2（T+1 加 0.1%）；覆盖亚太 22 个国家；2025 年可用率 99.98%。
- 结论：技术上今晚就能完成切换，主要工作量在改端点、密钥和 `merchant_ref` 字段并在沙箱验证。是否切换是业务决策，本报告不执行。

## 五、合规要求（PCI DSS）

根据 **PCI DSS v4.0** 第 12.10.1 条，支付处理中断（包括服务不可用）即使没有数据泄露，也属于需要记录和报告的"服务中断"：

- **24 小时内**记录事件：发生时间、受影响服务、估计受影响交易数、根因。
- **72小时内通知收单行/支付处理方**：事件摘要、客户影响评估、已采取的缓解措施、恢复时间线。
- 仅在怀疑数据泄露时才需通知持卡人；目前没有未授权访问的迹象。
- 故障超过 4 小时，部分卡组织要求通知；记录至少保留 12 个月。

本次故障从 14:30 UTC 算起至预计恢复已超过 4 小时，建议按 72小时时限（即 3 月 4 日 14:30 UTC 前）完成对收单行的报告。本报告未发送任何通知。
