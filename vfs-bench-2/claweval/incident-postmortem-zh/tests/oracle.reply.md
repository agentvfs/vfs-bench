# 2月28日生产环境故障复盘报告

## 一、事故概述

2026年2月28日20:15起，生产环境核心服务大面积异常：API超时、支付服务503、订单提交失败率95%以上、后台任务队列堆积超过5万条，至21:35服务恢复，持续约80分钟。

**根因**：CRM数据同步定时任务 **crm_data_sync（JOB-301）** 20:00自动触发后，执行了上周五（2月27日）发版新引入的**未优化SQL**：未走索引，**全表扫描**约1200万行。该进程持有300+数据库连接，导致主库**连接池耗尽（200/200）**，引发**级联**故障。DBA小王21:30手动终止该进程后，服务于21:35恢复。

## 三、根因分析

- **问题SQL**：`SELECT * FROM customers JOIN orders ON customers.id = orders.customer_id WHERE sync_status = 'pending'`，sync_status 没有索引，每次执行全表扫描约1200万行（TK-1908、msg_1902、JOB-301备注）。
- **引入来源**：2月27日发版的"CRM客户数据同步优化"改动，修改了同步查询逻辑（msg_1903）。
- **定时任务证据**：JOB-301 的执行记录显示，2/26、2/27 旧逻辑正常完成，耗时约3分钟（175秒、180秒）；2/28 新逻辑从20:00一直运行到21:30被手动终止（记录5400秒），期间持有300+连接。
- **资源占用**：主库连接池上限200，crm_data_sync 一个进程就持有300+连接，挤占了其他服务的连接（INT-204）。

结论：根因是CRM同步任务新SQL的全表扫描，而不是数据库本身；连接池耗尽、支付失败等都是症状。

## 四、因果链

1. **触发**：20:00 定时任务 JOB-301（crm_data_sync）自动启动。
2. **根因**：执行新引入、未经DBA评审和压测的SQL，未走索引，全表扫描。
3. **直接影响**：慢查询长时间占用300+数据库连接，**连接池耗尽（200/200）**。
4. **级联故障**：API超时（20:15）→ 支付服务503（20:25）→ 订单失败率95%+（20:28）→ Celery任务队列堆积5万条（20:40），CDN命中率随之下降。
5. **恢复**：21:30 DBA手动kill进程并暂停任务 → 连接池降至25% → 21:35 各服务恢复 → 21:50 告警解除。

## 五、影响评估

- **支付**：20:25–21:35 支付网关错误率100%，所有在线支付交易失败（INT-201）。
- **订单**：订单提交失败率95%以上；约**200笔订单**状态异常（部分支付成功但状态未更新，部分重复提交），需人工核对（TK-1911）。
- **用户**：页面无法加载、无法下单，客服收到约30条投诉。
- **后台任务**：Celery队列堆积超过5万条（订单确认邮件、库存同步、数据分析）。
- **持续时间**：20:15告警至21:35恢复，约80分钟。
- **当前恢复情况**：INT-204 主库已恢复，连接数45/200；INT-201 支付网关、INT-203 订单服务已恢复；**INT-202 CRM数据同步仍为 degraded（已暂停）**，需DBA添加索引后才能恢复。

## 六、流程缺陷

1. **跳过DBA评审**：CRM同步的SQL改动只由开发负责人评审，跳过了DBA性能评审（msg_1903）。
2. **DBA建议被否决**：发版评审会上DBA小王指出改动涉及JOIN查询，建议先在预发布环境做性能测试，因客户催得急未被采纳（NOTE-601）。
3. **未压测就发版**：同批的订单搜索改进做了压测，CRM改动没有；且计划周一上线，实际周五晚就部署了。
4. **定位慢**：20:15就有告警，20:45才定位到CRM同步进程，用了30分钟（NOTE-602）。
5. **系统性问题**：KB-602 规定单个进程不应占用超过连接池的25%、重型查询应走读副本，但都没有落实；这与12月事故是同一类问题。

## 七、历史事故关联

- **KB-603（2025年12月15日事故）**：报表聚合查询未走读副本，直接在主库执行，导致连接池压力过大、API超时，手动终止任务后恢复，模式与本次相同。
- 当时的改进措施"重型查询应使用读副本"标记为**TODO，至今未实施**；遗留问题中明确写了"CRM同步任务原计划迁移到读副本，至今未完成，类似事故可能再次发生"。
- 本次事故就是该**历史**遗留问题的重复发生，说明改进措施没有落地（NOTE-602 中运维总监也确认了这一点）。

## 八、改进建议

**短期（止血）**
1. 为 sync_status（及 orders.customer_id）添加**索引**，避免 `SELECT *`；优化后的查询经DBA评审并在预发布环境压测，通过后再恢复 JOB-301 和 INT-202。
2. 设置单进程/单任务的数据库连接上限（按KB-602，不超过连接池的25%，即50个），与核心交易服务的连接隔离。
3. 尽快完成 TK-1911 中约200笔异常订单的人工核对。

**长期（根治）**
4. 推进CRM同步迁移到**读副本**，完成KB-603遗留的TODO，指定责任人和完成时间。
5. 强制DBA性能评审：涉及SQL的变更必须经过DBA评审和压测，不能因时间紧迫跳过；实际**发版**时间须与评审结论一致。
6. 为定时任务增加运行时长告警（例如 JOB-301 超过正常3分钟的数倍即告警或自动终止），缩短根因定位时间。
7. 排查其他仍在主库执行的重型任务，跟踪改进项落地，并在72小时内将复盘报告归档到知识库（KB-601）。
